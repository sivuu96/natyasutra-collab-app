# Deployment

The hub ships as one container that runs the API and serves the built web app from the same address. It needs one PostgreSQL database. This guide deploys it on **Render** using the included Blueprint (`render.yaml`).

## What gets deployed

| Piece | Where | Notes |
|---|---|---|
| Web app + API + WebSockets | Render web service (Docker, from `deploy/Dockerfile`) | Migrations run on every start. Health check: `/health`. |
| Database | Render PostgreSQL (`natyasutra-hub-db`) | Connection string is injected automatically. |
| Bridge secret | Generated by Render (`BRIDGE_TOKEN_SECRET`) | Signs bridge tokens. Never commit it. |
| TLS (HTTPS) | Render | Certificates are automatic. Secure cookies are on by default. |

Serving the UI from the same address as the API avoids cross-origin cookies, so sign-in and live updates stay simple. The original plan put the UI on Vercel; this deployment does not need it.

## Cost: free plan (as configured in `render.yaml`)

Both resources use Render's free plan, so there is no charge. Its limits matter:

- **Web service:** sleeps after about 15 minutes without traffic. The first visit after a sleep takes roughly 30–60 seconds. Bridges reconnect automatically when it wakes.
- **PostgreSQL:** the free database **expires 30 days after it is created** and has **no backups**. Before the 30 days are up, either upgrade it in the Render dashboard or export your data. Plan for this now.

Plan limits can change. Check the Render pricing page before relying on them. You can change plans in the dashboard at any time.

## 1. Deploy

1. Sign in to Render with GitHub and authorise access to `sivuu96/natyasutra-collab-app`.
2. In Render: **New > Blueprint**, select the repository, and approve the two resources in `render.yaml`.
3. Wait for the first build. It takes a few minutes: the image builds the React app and installs the Python dependencies.
4. Open the service URL Render shows (for example `https://natyasutra-hub.onrender.com`). You should see the sign-in page.

Every push to `main` redeploys automatically (`autoDeploy: true`).

## 2. Create the first accounts

Registration is closed in the deployed configuration (`ALLOW_REGISTRATION=false`). Create accounts from the server:

1. In the Render dashboard, open the web service, then **Shell**.
2. Run, once per person:

   ```sh
   python -m scripts.manage create-user --email you@example.com --name "Your Name"
   ```

   It asks for a password twice, without echoing it.
3. Sign in on the web app, create a team and a project, and add teammates by their email. They must already have an account.

To reopen registration, set `ALLOW_REGISTRATION` to `true` in the Render dashboard. Set it back to `false` when you're done.

### Forgotten password

```sh
python -m scripts.manage set-password --email you@example.com
```

This ends every session for that account, so anyone who had its password loses access too.

## 3. Connect a team member's machine (bridge)

The hub never reaches into a machine. Each person runs the bridge locally:

1. In the web app, open **Devices**, enter a machine name, and create a pairing code.
2. Run the command the page shows, with your hub address, for example:

   ```powershell
   collab-bridge pair --hub https://natyasutra-hub.onrender.com --code ABCD-EFGH --name "Work laptop"
   ```

3. Add an agent and start the bridge (see `bridge/README.md`), then offer the agent to a project from the **Agents** tab.

Agents run on that person's own computer with their own Claude Code or Codex login. The hub stores coordination data and transcripts only.

## 4. Configuration reference

Set these in Render (**Environment**). The Blueprint sets the first four.

| Variable | Value | Purpose |
|---|---|---|
| `DATABASE_URL` | from the database | PostgreSQL connection. `postgres://` URLs are accepted. |
| `BRIDGE_TOKEN_SECRET` | generated, at least 32 characters | Signs bridge tokens. Required in production. |
| `ALLOW_REGISTRATION` | `false` | Open or close self-service sign-up. |
| `LOG_LEVEL` | `INFO` | Log verbosity. |
| `ENVIRONMENT` | `production` (set in the image) | Enables secure cookies, HSTS, and the production checks. |
| `CORS_ORIGINS` | optional, comma-separated | Extra allowed origins, for example a custom domain. The Render URL is added automatically. |
| `COOKIE_SECURE` | leave unset | Only set `false` for plain-HTTP local testing. |

The app refuses to start in production if `BRIDGE_TOKEN_SECRET` is missing or short, or if the database is not PostgreSQL.

## 5. Operating it

- **Health:** `GET /health` (process up), `GET /ready` (database reachable).
- **Logs:** Render dashboard. Logs are JSON, one line per event. The app does not log message text, and a filter redacts bearer tokens and password-like fields, but that filter is pattern-based and not yet tested (`docs/security.md` §10).
- **Scaling:** keep **one instance**. The realtime hub and rate limiter are in-process. Several instances would miss live updates and split rate limits (`docs/security.md` §10).
- **Backups:** the free PostgreSQL plan has no backups. Export the data (`pg_dump` from the Render dashboard's connection details) regularly, and before the database's 30-day expiry. Upgrade to a paid plan for automatic backups.
- **Upgrades:** push to `main`. Migrations run before the server starts, so a failed migration stops the new version from starting. Render should keep the previous version serving in that case; confirm this on your first failed deploy.

## 6. Run the production image on your own machine

Useful for testing a release before it goes out:

```powershell
# deploy/.env must contain BRIDGE_TOKEN_SECRET=<32+ random characters>
docker compose -f deploy/docker-compose.yml up --build
# open http://localhost:8080
```

`COOKIE_SECURE=false` is set only in this local file, because plain HTTP cannot carry secure cookies.

## Known limits of this deployment

- Free-plan limits: the web service sleeps when idle, and the database expires after 30 days with no backups (see Cost above).
- No automatic monitoring or alerting yet. Watch the health check in Render, or add an external uptime monitor. An external monitor that pings `/health` also keeps the free service awake.
- No password reset by email. Use the operator command.
- No multi-factor sign-in.
- Rate limits are per process. Fine for one instance.
- Security headers are set by the app. Review them with your own scan before opening the hub to people outside the team.
