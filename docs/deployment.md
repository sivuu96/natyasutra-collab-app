# Deployment

The hub ships as one container that runs the API and serves the built web app from the same address. It needs one PostgreSQL database. This guide runs the container on **Render** (using the included Blueprint, `render.yaml`) and the database on **Supabase**.

## What gets deployed

| Piece | Where | Notes |
|---|---|---|
| Web app + API + WebSockets | Render web service (Docker, from `deploy/Dockerfile`) | Migrations run on every start. Health check: `/health`. |
| Database | Supabase PostgreSQL (free plan) | Set `DATABASE_URL` by hand in Render. See "Database (Supabase)" below. |
| Bridge secret | Generated by Render (`BRIDGE_TOKEN_SECRET`) | Signs bridge tokens. Never commit it. |
| TLS (HTTPS) | Render | Certificates are automatic. Secure cookies are on by default. |

Serving the UI from the same address as the API avoids cross-origin cookies, so sign-in and live updates stay simple. The original plan put the UI on Vercel; this deployment does not need it.

## Cost: free plans (as configured)

Both the web service (Render) and the database (Supabase) use free plans, so there is no charge. Their limits matter:

- **Web service (Render):** spins down after 15 minutes without inbound traffic. Waking it takes about one minute. Bridges reconnect automatically when it wakes. The filesystem is ephemeral; the hub stores everything in PostgreSQL, so this is safe. Monthly hours: 750 free instance hours per workspace. One always-on instance uses about 744 hours in a 31-day month, so this fits, but no other free services can share it.
- **Database (Supabase free):** **projects pause after a week of inactivity**. The data is kept, but the hub is down until someone restores the project in the Supabase dashboard. Storage is capped at **500 MB**. There are **no automatic backups** on the free plan.

Sources: [Render free plan documentation](https://render.com/docs/free), [Supabase pricing](https://supabase.com/pricing).

Plan limits can change. Check the Render and Supabase pricing pages before relying on them. You can change plans in either dashboard at any time.

## Database (Supabase)

The hub uses a Supabase PostgreSQL project. Create it in the region closest to the Render service (`render.yaml` uses Oregon, so choose **us-west-2**). Keep the database password somewhere safe.

**Connection string.** Use the **Session pooler** URI from Supabase (**Connect > Session pooler**), which looks like:

`postgresql://postgres.<project-ref>:<password>@aws-<n>-<region>.pooler.supabase.com:5432/postgres?sslmode=require`

- Use the **Session pooler on port 5432**. The direct connection (`db.<project-ref>.supabase.co`) is IPv6-only, and Render cannot reach it.
- Do not use the Transaction pooler (port 6543) unless you also set `prepare_threshold=None` in the app. The app does not do this today.
- If the password contains special characters such as `@`, URL-encode them (`@` becomes `%40`). Otherwise the URL is parsed wrongly.
- Set this value as `DATABASE_URL` in Render (**Environment**). Never commit it.

**Security (required).** Supabase's Data API exposes tables in the `public` schema to the `anon` and `authenticated` roles by default. The hub's tables are in `public`, so after the schema is in place (the first start runs the migrations), enable row-level security on every table and revoke those roles' access:

```sql
-- Run as the postgres role in the Supabase SQL editor, after the first deploy has created the tables.
DO $$
DECLARE r record;
BEGIN
  FOR r IN SELECT tablename FROM pg_tables WHERE schemaname = 'public' LOOP
    EXECUTE format('ALTER TABLE public.%I ENABLE ROW LEVEL SECURITY', r.tablename);
  END LOOP;
END $$;
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon, authenticated;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM anon, authenticated;
REVOKE ALL ON ALL FUNCTIONS IN SCHEMA public FROM anon, authenticated;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON TABLES FROM anon, authenticated;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON SEQUENCES FROM anon, authenticated;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON FUNCTIONS FROM anon, authenticated;
```

The hub connects as `postgres`, which still has access. Confirm that `set role anon; select count(*) from users;` returns a permission error.

**Moving an existing database.** Dump from the old database with `pg_dump -Fc --no-owner --no-privileges`, restore with `pg_restore --no-owner --no-privileges --exit-on-error` into the new project, compare row counts and `alembic_version`, then apply the security SQL above and update `DATABASE_URL`. Use a PostgreSQL 18 client for the dump, because the Supabase project runs PostgreSQL 17 and the dump tool must not be older than the server it dumps.

**Backups.** The Supabase free plan has no automatic backups. Export the data with `pg_dump` on a regular schedule, and keep the files somewhere you control. Paid plans include daily backups.

## 1. Deploy

1. Sign in to Render with GitHub and authorise access to `sivuu96/natyasutra-collab-app`.
2. In Render: **New > Blueprint**, select the repository, and approve the web service in `render.yaml`.
3. In the service's **Environment** tab, set `DATABASE_URL` to the Supabase Session pooler URL (see above). The Blueprint does not set it, so the first deploy will fail until you do.
4. Wait for the first build. It takes a few minutes: the image builds the React app and installs the Python dependencies.
5. Open the service URL Render shows (for example `https://natyasutra-hub.onrender.com`). You should see the sign-in page.

Every push to `main` redeploys automatically (`autoDeploy: true`).

## 2. Create the first accounts

Registration is closed in the deployed configuration (`ALLOW_REGISTRATION=false`). Create accounts from the server:

1. In the Render dashboard, open the web service, then **Shell**.
2. Run, once per person:

   ```sh
   python -m scripts.manage create-user --email you@example.com --name "Your Name"
   ```

   It asks for a password twice, without echoing it.
3. Sign in on the web app, create a team and a project, and add teammates by their email. They must already have an account.

To reopen registration, set `ALLOW_REGISTRATION` to `true` in the Render dashboard. Set it back to `false` when you're done.

### Forgotten password

```sh
python -m scripts.manage set-password --email you@example.com
```

This ends every session for that account, so anyone who had its password loses access too.

## 3. Connect a team member's machine (bridge)

The hub never reaches into a machine. Each person runs the bridge locally:

1. In the web app, open **Devices**, enter a machine name, and create a pairing code.
2. Run the command the page shows, with your hub address, for example:

   ```powershell
   collab-bridge pair --hub https://natyasutra-hub.onrender.com --code ABCD-EFGH --name "Work laptop"
   ```

3. Add an agent and start the bridge (see `bridge/README.md`), then offer the agent to a project from the **Agents** tab.

Agents run on that person's own computer with their own Claude Code or Codex login. The hub stores coordination data and transcripts only.

## 4. Configuration reference

Set these in Render (**Environment**). The Blueprint sets all except `DATABASE_URL`, which you set by hand.

| Variable | Value | Purpose |
|---|---|---|
| `DATABASE_URL` | Supabase Session pooler URL (set by hand) | PostgreSQL connection. `postgres://` URLs are accepted. |
| `BRIDGE_TOKEN_SECRET` | generated, at least 32 characters | Signs bridge tokens. Required in production. |
| `ALLOW_REGISTRATION` | `false` | Open or close self-service sign-up. |
| `LOG_LEVEL` | `INFO` | Log verbosity. |
| `ENVIRONMENT` | `production` (set in the image) | Enables secure cookies, HSTS, and the production checks. |
| `CORS_ORIGINS` | optional, comma-separated | Extra allowed origins, for example a custom domain. The Render URL is added automatically. |
| `COOKIE_SECURE` | leave unset | Only set `false` for plain-HTTP local testing. |

The app refuses to start in production if `BRIDGE_TOKEN_SECRET` is missing or short, or if the database is not PostgreSQL.

## 5. Operating it

- **Health:** `GET /health` (process up), `GET /ready` (database reachable).
- **Logs:** Render dashboard. Logs are JSON, one line per event. The app does not log message text, and a filter redacts bearer tokens and password-like fields, but that filter is pattern-based and not yet tested (`docs/security.md` §10).
- **Scaling:** keep **one instance**. The realtime hub and rate limiter are in-process. Several instances would miss live updates and split rate limits (`docs/security.md` §10).
- **Backups:** the Supabase free plan has no automatic backups. Export the data regularly with `pg_dump` using the Session pooler URL, and keep the files somewhere you control. Upgrade to a paid Supabase plan for automatic backups.
- **Upgrades:** push to `main`. Migrations run before the server starts, so a failed migration stops the new version from starting. Render should keep the previous version serving in that case; confirm this on your first failed deploy.

## 6. Run the production image on your own machine

Useful for testing a release before it goes out:

```powershell
# deploy/.env must contain BRIDGE_TOKEN_SECRET=<32+ random characters>
docker compose -f deploy/docker-compose.yml up --build
# open http://localhost:8080
```

`COOKIE_SECURE=false` is set only in this local file, because plain HTTP cannot carry secure cookies.

## Known limits of this deployment

- Free-plan limits (see Cost above and the README): the web service spins down when idle, and the Supabase database pauses after a week of inactivity and has no backups.
- The Supabase database lives in a different provider from the web service. Keep both free-plan limits in mind when planning maintenance.
- No automatic monitoring or alerting yet. Watch the health check in Render, or add an external uptime monitor. Pinging `/health` every few minutes keeps the free service awake all month; that is within the 750-hour allowance for one service.
- No password reset by email. Use the operator command.
- No multi-factor sign-in.
- Rate limits are per process. Fine for one instance.
- Security headers are set by the app. Review them with your own scan before opening the hub to people outside the team.
